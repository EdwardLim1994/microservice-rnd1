## User Story 1: User Registration

**Persona:** A new user visiting the application for the first time
**Goal:** Create an account using email and password
**Outcome:** They have an account in authentik and can proceed to sign in

### Acceptance Criteria
1. A user can submit email and password and an account is created in authentik
2. Submitting a duplicate email returns a clear error message to the client
3. Submitting an empty email or password returns a client-side validation error before the mutation is called
4. The register mutation is accessible through Apollo Router, not by calling the auth subgraph directly

### e2e Test Plan (Playwright)
- Scenario 1: Given a user is on the register page, when they submit a valid email and password, then a success message is displayed and an account exists in authentik
- Scenario 2: Given a user is on the register page, when they submit an email that is already registered, then a duplicate email error message is displayed
- Scenario 3: Given a user is on the register page, when they submit with an empty email field, then a validation error is shown and the mutation is not called
- Scenario 4: Given a user is on the register page, when they submit with an empty password field, then a validation error is shown and the mutation is not called

### Features

#### Feature 1.1: Auth GraphQL Subgraph Scaffold
- **Type:** backend
- **Description:** Scaffold a new TypeScript microservice under `./servers` using the repo's existing service generator. This service is the auth subgraph and is the single backend service for all auth mutations in this release. It must follow the same structure and conventions as other services in `./servers`.
- **Endpoint / Component:** GraphQL subgraph — `register` mutation
- **Input:** `mutation register(email: String!, password: String!)`
- **Output:** `{ success: Boolean!, message: String! }` on success; structured GraphQL error on failure
- **Edge cases:** Authentik API is unreachable (return a service unavailable error); authentik returns a duplicate user error (surface as a user-facing duplicate email error); password does not meet authentik's minimum policy (surface policy error message from authentik); empty or malformed email/password (reject at the resolver level before calling authentik)

#### Feature 1.2: Apollo Router Subgraph Wiring
- **Type:** backend
- **Description:** Register the auth subgraph in the Apollo Router's existing supergraph config so the `register`, `login`, and `logout` mutations are routable through Apollo Router. The repo already has a pipeline for promoting subgraphs — follow that existing pattern. This feature covers wiring for all three mutations in this release, not just `register`.
- **Endpoint / Component:** Apollo Router supergraph config
- **Input:** Auth subgraph URL and schema
- **Output:** Apollo Router correctly routes auth mutations to the auth subgraph; calling the auth subgraph URL directly is not required to be blocked, but the mutations must be verified as reachable via the router
- **Edge cases:** Auth subgraph is down when Apollo Router starts (router should start but return an error on auth mutation calls); schema composition fails due to type conflicts with other subgraphs (surface as a composition error and do not deploy)

#### Feature 1.3: Authentik Terraform and Helm Configuration
- **Type:** backend
- **Description:** Claude Code must read the existing Terraform and Helm files for authentik in the repo. If an OAuth2/OIDC application, client credentials (client ID and secret), enrollment flow, and authentication flow are not already defined, Claude Code must add the necessary Terraform resources. If they are already defined, Claude Code must read the existing values and use them as configuration for the auth service. The goal is for authentik to be fully configured and ready for the auth subgraph to call against, both locally and in Kubernetes.
- **Endpoint / Component:** Terraform authentik provider resources; Helm values for authentik
- **Input:** Existing Terraform/Helm files in the repo
- **Output:** Authentik has a configured OAuth2/OIDC application, a client ID and secret accessible to the auth service, an enrollment flow for registration, and an authentication flow for login and logout
- **Edge cases:** Terraform state conflicts with existing resources (do not recreate existing resources; use `terraform import` guidance if needed); client secret is not yet stored in a Kubernetes secret or environment variable (create the appropriate secret manifest or reference); authentik Helm deployment is not yet running in the local environment (surface this as a prerequisite and do not proceed with auth service calls until authentik is healthy)

#### Feature 1.4: Register UI
- **Type:** frontend
- **Description:** A simple React page at `/register` with an email field, password field, and submit button. On submit, calls the `register` mutation via Apollo Router. Displays a success message on success and an error message on failure. No styling requirements beyond basic HTML usability.
- **Endpoint / Component:** `RegisterPage` React component; React Router route `/register`
- **Input:** User-entered email and password; form submit action
- **Output:** Success message rendered on screen on success; error message rendered on screen on failure; no navigation on success (keep it simple)
- **Edge cases:** Apollo Router is unreachable (display a network error message); mutation returns a GraphQL error (display the error message from the response); user submits with empty fields (show inline validation before calling the mutation)
- **Claude Design URL:** [PENDING — Claude Design URL required before Claude Code begins]
- **UI Interactions:** Empty field validation shown inline on submit attempt; error message displayed below the form on API failure; success message replaces the form or displays below it on success; loading state on the submit button while the mutation is in flight
- **Responsive breakpoints:** inherit from design system

### Integration Test Plan
- Scenario 1: Call the `register` mutation via Apollo Router with a valid email and password — expect `{ success: true }` and confirm the user exists in authentik
- Scenario 2: Call the `register` mutation via Apollo Router with a duplicate email — expect a structured GraphQL error with a duplicate email message
- Scenario 3: Call the `register` mutation via Apollo Router with an empty email — expect a GraphQL validation error
- Scenario 4: Call the `register` mutation via Apollo Router with an empty password — expect a GraphQL validation error
- Scenario 5: Call the `register` mutation directly against the auth subgraph URL with a valid payload — expect it to succeed (subgraph is not required to be externally blocked in this release)

## User Story 2: User Sign In

**Persona:** A registered user returning to the application
**Goal:** Sign in with their email and password
**Outcome:** They receive a full token set stored in localStorage and are confirmed as authenticated

### Acceptance Criteria
1. A registered user can sign in with correct credentials and receive a full token set (access, refresh, and ID token)
2. An incorrect password returns a clear error message to the client
3. A non-existent email returns a clear error message to the client
4. On successful login, the full token set is stored in localStorage
5. The login mutation is accessible through Apollo Router

### e2e Test Plan (Playwright)
- Scenario 1: Given a registered user is on the sign-in page, when they submit correct credentials, then a success message is shown and localStorage contains the full token set
- Scenario 2: Given a user is on the sign-in page, when they submit an incorrect password, then a clear error message is displayed and localStorage is not written to
- Scenario 3: Given a user is on the sign-in page, when they submit an email that does not exist, then a clear error message is displayed and localStorage is not written to
- Scenario 4: Given a user is on the sign-in page, when they submit with empty fields, then a validation error is shown and the mutation is not called

### Features

#### Feature 2.1: Login Mutation
- **Type:** backend
- **Description:** Expose a `login` GraphQL mutation on the auth subgraph. Accept email and password, authenticate against authentik using the configured OAuth2/OIDC client credentials and authentication flow, and return the full token set on success.
- **Endpoint / Component:** GraphQL subgraph — `login` mutation
- **Input:** `mutation login(email: String!, password: String!)`
- **Output:** `{ accessToken: String!, refreshToken: String!, idToken: String! }` on success; structured GraphQL error on failure
- **Edge cases:** Authentik API is unreachable (return a service unavailable error); incorrect password (return an invalid credentials error — do not distinguish between wrong password and wrong email in the error message surfaced to the client, for security); non-existent email (return the same invalid credentials error); authentik returns an unexpected response shape (log the raw response and return a generic server error)

#### Feature 2.2: Sign In UI and Token Storage
- **Type:** frontend
- **Description:** A simple React page at `/login` with an email field, password field, and submit button. On submit, calls the `login` mutation via Apollo Router. On success, stores the full token set (access, refresh, and ID token) in localStorage and displays a success message. On failure, displays an error message.
- **Endpoint / Component:** `LoginPage` React component; React Router route `/login`
- **Input:** User-entered email and password; form submit action
- **Output:** On success — full token set written to localStorage keys `auth_access_token`, `auth_refresh_token`, `auth_id_token`; success message rendered. On failure — error message rendered; localStorage not written to
- **Edge cases:** Apollo Router is unreachable (display a network error message); mutation returns a GraphQL error (display the error message); localStorage is unavailable (catch the exception and display a storage error message); user submits with empty fields (show inline validation before calling the mutation)
- **Claude Design URL:** [PENDING — Claude Design URL required before Claude Code begins]
- **UI Interactions:** Empty field validation shown inline on submit attempt; loading state on the submit button while the mutation is in flight; error message displayed below the form on failure; success message displayed on success
- **Responsive breakpoints:** inherit from design system

### Integration Test Plan
- Scenario 1: Call the `login` mutation via Apollo Router with valid credentials — expect a response containing `accessToken`, `refreshToken`, and `idToken`
- Scenario 2: Call the `login` mutation via Apollo Router with an incorrect password — expect a structured GraphQL error with an invalid credentials message
- Scenario 3: Call the `login` mutation via Apollo Router with a non-existent email — expect a structured GraphQL error with an invalid credentials message
- Scenario 4: Call the `login` mutation via Apollo Router with empty email and password — expect a GraphQL validation error

## User Story 3: User Sign Out

**Persona:** A signed-in user who wants to end their session
**Goal:** Sign out of the application
**Outcome:** Their localStorage is cleared and their session is fully invalidated in authentik via RP-initiated logout

### Acceptance Criteria
1. A signed-in user can sign out and their localStorage tokens are cleared
2. After sign out, the authentik session is fully invalidated server-side, not just cleared locally
3. Attempting to sign out with an invalid or expired token returns a clear error message
4. The logout mutation is accessible through Apollo Router

### e2e Test Plan (Playwright)
- Scenario 1: Given a signed-in user is on the sign-out page, when they click sign out, then localStorage is cleared and a success message is displayed
- Scenario 2: Given authentik confirms the session is invalidated after logout, when the same token is used in a subsequent logout call, then an invalid or expired token error is returned
- Scenario 3: Given a user calls logout with a malformed or missing token, then a clear error message is returned and localStorage is not affected by the backend (frontend should still clear localStorage)

### Features

#### Feature 3.1: Logout Mutation
- **Type:** backend
- **Description:** Expose a `logout` GraphQL mutation on the auth subgraph. Accept the access token, perform a full RP-initiated logout against authentik to invalidate the server-side session and revoke the token, and return success or error.
- **Endpoint / Component:** GraphQL subgraph — `logout` mutation
- **Input:** `mutation logout(accessToken: String!)`
- **Output:** `{ success: Boolean!, message: String! }` on success; structured GraphQL error on failure
- **Edge cases:** Authentik API is unreachable (return a service unavailable error); token is already expired or invalid (return a clear invalid token error); authentik returns an unexpected response on the logout call (log the raw response and return a generic server error); empty token string passed (reject at the resolver level before calling authentik)

#### Feature 3.2: Sign Out UI
- **Type:** frontend
- **Description:** A simple React page or component at `/logout` with a sign-out button. On click, reads the access token from localStorage, calls the `logout` mutation via Apollo Router, and on success clears all auth keys from localStorage and displays a success message. On failure, displays an error message but still clears localStorage.
- **Endpoint / Component:** `LogoutPage` React component; React Router route `/logout`
- **Input:** Sign-out button click; access token read from localStorage `auth_access_token`
- **Output:** On success — `auth_access_token`, `auth_refresh_token`, `auth_id_token` removed from localStorage; success message rendered. On failure — error message rendered; localStorage still cleared on the client side regardless of backend response
- **Edge cases:** No token found in localStorage when sign out is clicked (skip the mutation call, clear localStorage anyway, display a message that the user was not signed in); Apollo Router is unreachable (clear localStorage anyway and display a network error message); mutation returns a GraphQL error (clear localStorage anyway and display the error message)
- **Claude Design URL:** [PENDING — Claude Design URL required before Claude Code begins]
- **UI Interactions:** Loading state on the sign-out button while the mutation is in flight; success message displayed after localStorage is cleared; error message displayed if the mutation fails (localStorage still cleared)
- **Responsive breakpoints:** inherit from design system

### Integration Test Plan
- Scenario 1: Call the `logout` mutation via Apollo Router with a valid access token — expect `{ success: true }` and confirm the session is invalidated in authentik
- Scenario 2: Call the `logout` mutation via Apollo Router with an already-invalidated token — expect a structured GraphQL error with an invalid token message
- Scenario 3: Call the `logout` mutation via Apollo Router with an empty token string — expect a GraphQL validation error
- Scenario 4: Call the `logout` mutation via Apollo Router with a malformed token — expect a structured GraphQL error
